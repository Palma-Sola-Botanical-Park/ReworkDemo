# PART 1 — For Human Webmasters

## How the site is wired

### Shared shell — `js/site.js` is the brain
Every page is a thin HTML file that:
1. links `css/site.css`,
2. has empty `<div id="nav-placeholder">` and `<div id="footer-placeholder">` divs,
3. loads `js/site.js`,
4. calls `injectShared({ ... })`.

`injectShared()` injects the shared nav and footer into those placeholders — so nav/footer
are defined **once** in `site.js` and appear on every page. Change them there, not per-page.

Options for `injectShared()`:
- `inatBar: true` — builds the live iNaturalist stats bar into `#inat-bar-placeholder`
- `inatFooter: true` — injects iNaturalist stats into the footer
- (omit/false = neither). If you set either, also call `loadINat()` to populate it.

### The link router — `viewer.html`
`site.js` decides how every content link behaves based on the URL:
- internal page → same window
- external site → new tab
- **PDF or published Google Doc → framed inside `viewer.html`** (in-site, with a Back button)
- `mailto:` / `tel:` → native

`viewer.html` is **not a nav page** — it's a shared subroutine the router points at. **Do not delete it.**

## Data layer

Two sources: **static JSON files** (baked from HTML pages) and **live Google Sheets** (read at page load).

### Static JSON (committed to repo root)
| File | What it is | Generated by |
|------|-----------|--------------|
| `plants.json` | Flattened summary of all plant pages (~122) — feeds Plants tab search/filter | `data/scripts/generate_plants_json.py` |

### Live Google Sheets (read at page load)
`events`, `classes`, `announcements`, `volunteer`, `newsletters`, `news` are pulled live via
`fetchTab(gid)` in `site.js`, fetched as CSV:
`https://docs.google.com/spreadsheets/d/<SHEET_ID>/export?format=csv&gid=<GID>`

The sheet must be shared **"Anyone with the link → Viewer"** or the fetch fails.

> These live tabs currently have **no offline fallback** — if Google is slow/down, those tabs come up empty. (Planned: nightly bake to JSON + stale-while-revalidate, same pattern as plants/wildlife. See backlog B2.)

## Naming & placeholder conventions

- **PSBP IDs:** plants `PSBP-00001`–`00122+`; wildlife `PSBP-99970`–`99999`.
- A species has a page (`plants/` or `wildlife/`) **and** a photo (`photos/`) sharing the same ID, **hyphenated** (e.g. `PSBP-00001-Tree-Crinum.html` ↔ `PSBP-00001-Tree-Crinum.jpg`).
- **Wildlife page theme colors:** green = plants, **blue = birds** (sky), **pink = butterflies**, **brown = reptiles/mammals/bugs** (earth). The `theme-*` class lives on `.wild-wrap`.
- **Placeholder images** (when a species lacks a usable photo — usually a licensing gap): copy the matching theme-color master and rename to the species' PSBP filename. Masters in `photos/`: `PLACEHOLDER-plant-green.jpg`, `PLACEHOLDER-bird-blue.jpg`. Pink/brown made on-demand only (none needed yet).

## Content build pipeline (how plant & wildlife pages are made)

This is the process behind every field-guide page — research → spreadsheets → script → HTML. It is **separate from the live site**: it produces the static pages and JSON the site reads. Two parallel tracks (plants and wildlife) that work identically.

### The source files (all in `data/sources/`)

| File | Role |
|------|------|
| `PSBP_Master_Plant_Signage.xlsx` | **The master content** for every plant — one row per species. (Wildlife: `PSBP_Master_Animal_Signage.xlsx`.) |
| `Plants_and_Wildlife_Photo_Credits.csv` | **Photo attribution** — who took each photo / source / license, keyed to the species. |

The plant signage workbook has three tabs: `PSBP_Plants` (one row per species, ~30 columns), `Placements` (physical instances — see the species-vs-instance note), and an `Export Summary`. The `PSBP_Plants` columns group into:
- **Identity:** Common Name, Botanical Name, PSBP Species ID, Family, Genus, Species, Cultivar, Alternate Names
- **Content prose:** Quick Hits, Origin, More Information, Wildlife Value, Reproduction and Identification, Size, Growing Conditions
- **Safety flags (each a Green/Yellow/Red flag + a prose field):** Edibility, Toxicity / Toxic to People, Toxic to Dogs, Invasive (+ Invasive Notes); plus Native or Non-native
- **Housekeeping:** Sign Level, Has Sign, Category, Feature Tier, Other Notes, Internal Notes

### The build flow

1. **Research the species** and fill in its row in the signage spreadsheet. *Accuracy is paramount* (Bev flags AI errors) — defer to firsthand on-site observation over textbook descriptions; flag blanks rather than fabricate.
2. **Source a usable photo** (right to use it — licensing matters; see the placeholder convention for photo-less species) and **record its credit** in the photo-credits CSV.
3. **Run the page generator** — `data/scripts/generate_plant_pages.py` reads the **plant signage spreadsheet + the photo-credits CSV together** and writes the HTML field-guide page into `plants/`, with the **photo attribution rendered on the page**.
   - *How it actually runs:* the generator runs **inside a Claude chat session**, not on your Mac. Upload three files (master xlsx, credits CSV, and `PSBP-00003-Buccaneer-Palm.html` as the style reference), Claude runs the script in its sandbox, and you download the output HTML. The script's `/mnt/user-data/uploads/…` paths are sandbox paths, not local. The reference page's `<head>` (including all CSS) is stamped onto every generated page; its `<body>` is rebuilt from scratch each run.
   - *Wildlife note:* there is **no** `generate_wildlife_pages.py`. The ~30 wildlife pages in `wildlife/` were built by another means (hand-built, or a one-off / retired process — **confirm with Randy**). Only the wildlife *search index* (`generate_wildlife_json.py`, step 4) is a standing tool. If wildlife pages need regenerating in bulk, that page-builder does not currently exist.
4. **Run the search-index generator** — `data/scripts/generate_plants_json.py` reads the finished HTML pages and writes `plants.json` (the search/filter index). `generate_wildlife_json.py` does the same for `wildlife.json`. (These read the HTML; they are *not* page builders.)
5. **Commit + push.**

### Where credit appears (and where it doesn't)

- **Full field-guide page** (`plants/PSBP-*.html`): photo **with** its attribution credit.
- **Search-result card** (built from `plants.json`): the **same photo, no credit line**. Credit lives only on the full page, by design. If credit display in search results is ever wanted, it would mean adding the credit field to the JSON generator's output.

> The signage spreadsheet is the **single source of truth** for content. Edit there and regenerate — don't hand-edit finished HTML pages (changes get overwritten on the next build, and it breaks the derive-don't-scrape rule).

## Project vision (the why)

Started **May 18 2026** as a simple idea: use iNaturalist to track species in the park. It grew into the
park's connective infrastructure — field guide, content backend, signage system, eventual public web presence.
The rollout sequence Randy committed to (and it matters — don't propose leapfrogging it): **signs → tours → web**,
in that order, "each one earns the next." QR codes on plant signs are the opening move.

The master signage spreadsheet is effectively a **"Signs" generator** — the goal is a QR sign at every plant
that scans to its field-guide page.

## Architecture philosophy (internalize these)

1. **Single source of truth.** Everything derives from the master spreadsheet → scripts bake → JSON/HTML the
   site reads. **Never scrape rendered HTML to recover data.** Every filter bug in this project traced back to
   HTML regex scraping of badge text. Derive flags from master columns / category instead.
2. **Three layers:** *authoring* (Google Sheets + the `data/` workshop) → *conveyor belt* (scripts in
   `data/scripts/`) → *runtime* (the JSON files the site reads). `data/` is a **workshop, never read by the
   live site.** Don't wire runtime to anything in `data/`.
3. **The runtime should depend on nothing but repo files.** Google is where Bev *edits*; a script is the only
   thing that should *touch* Google. (This is the direction of the planned JSON-exclusive migration.)
4. **`site.js` is the brain.** Key members: `NAV_HTML`, `FOOTER_HTML`, `injectShared()`, the link router
   (`PSBP.linkKind` / `linkAttrs` / `linkTag` / `rowLink`), `fetchTab()`, `loadINat()`, `loadEvents()`,
   `loadClasses()`, `loadAnnouncements()`, `loadVolSpotlight()`, `loadPlants()` / `plantCard()` /
   `renderPlants()` / `filterPlants()` / `toggleFilter()`, `isWebVisible()`.
5. **`viewer.html` is load-bearing.** It's the in-site document renderer the link router points PDFs and
   published Google Docs at — not a nav page. Deleting it breaks document links across events/announcements/etc.

## Gotchas & hard-won lessons (do not relearn these)

- **Photo naming uses HYPHENS, folder `photos/`:** `PSBP-00001-Tree-Crinum.jpg`. An old standalone gallery used
  underscores (`PSBP-00001_Tree_Crinum.jpg`) and is dead/retired. If you see underscores, it's the fossil.
- **Renames create duplicate pages.** When a plant's common name changes and you regenerate, a NEW file is
  created; the OLD one must be deleted or `plants.json` gets duplicate cards + an inflated count. This bit the
  project repeatedly (Acerola/Barbados-Cherry, Whorled-Pennywort/Dollarweed, Trailing-Daisy/Wedelia,
  Groundsel-Tree/Saltbush, Frangipani/Mexican-Plumeria, Geiger-tree case). The slash-in-name → double-underscore
  filename mess is what started it. **After any rename pass, run the duplicate check and reconcile.**
- **`site.js` has historically reverted to OLD Sheet IDs when regenerated.** Always verify `SHEET_ID` after any
  regeneration of site.js.
- **Running `restyle_plants.py` multiple times once caused duplicate footer blocks.** Cautionary tale about
  non-idempotent batch scripts.
- **The em-dash incident:** a prior session used em-dash separators instead of colons in the
  Reproduction/Identification column across ~68 pages; a global fix was applied. Don't reintroduce em-dashes there.
- **iNaturalist GPS is sloppy** (bad signal, many yards off). Do NOT use it for sign/instance location — use
  Google Earth / KML hand-placed coordinates as the master location. (See Placements below.)
- **In-site PDFs must be same-origin (repo) or a published Google Doc.** `viewer.html` renders via PDF.js, which
  *fetches* the bytes with JS → subject to CORS. Third-party file hosts (Mailchimp `mcusercontent.com`, etc.)
  block cross-origin reads, so the raw link works but the in-site embed renders blank. Host embeddable PDFs in
  the repo (`docs/news/`). (Incident 2026-06-14, resolved by rehosting.)
- **Content build pipeline (see PART 1 for full detail):** plant field-guide pages are built from
  `data/sources/PSBP_Master_Plant_Signage.xlsx` (content) + `Plants_and_Wildlife_Photo_Credits.csv` (attribution)
  by `generate_plant_pages.py` → HTML pages **with photo credit shown** → `generate_plants_json.py` → `plants.json`
  (search index, **same photo, no credit**). **There is NO `generate_wildlife_pages.py`** — wildlife pages were
  built by another (hand/one-off/retired) means; only `generate_wildlife_json.py` (search index) is standing. The
  signage spreadsheet is the **single source of truth** — never hand-edit finished plant HTML (overwritten on
  rebuild). Recurring back-and-forth on page-build details + master-spreadsheet column conventions; treat the
  spreadsheet columns + the generator as the contract, and confirm with Randy before changing either.

## Content voice & accuracy rules

- **Accuracy first** — Bev flags AI errors. When categorizing plants, **defer to Randy's firsthand on-site
  observation over textbook descriptions.** When unsure, ask rather than fabricate.
- **Quick Hits** lead with a park-specific, local-interest hook; park anecdotes belong here when strong.
- **Edibility badge** reads "✅ Non-Toxic" (never "Edible & Safe") for plants that aren't food-safe.
- **Avoid stale time-based phrasing** (e.g. "recently," specific counts that age out).
- Randy pushes for **readable type** (min ~1rem body), same-tab nav, warm community-first copy ("Let's roll" energy).

## Data model: species vs. instances (the Placements layer)

- One HTML page = one **species** profile. A species can have **multiple physical instances** (e.g. 4 Staghorn
  Ferns), each getting its own QR sign.
- The master signage workbook (`data/sources/PSBP_Master_Plant_Signage.xlsx`) has a **`Placements` tab**:
  `Placement ID` (PLC-####, the stable per-instance anchor) · `PSBP Species ID` (FK to the species page) ·
  Area of Park · Latitude · Longitude · Status · Notes. Schema is **multi-instance-ready** — adding instances =
  add PLC rows sharing one `PSBP Species ID`. Keep species ID as the anchor; instances hang off it as children.
- **Location master = Google Earth / KML**, deliberately hand-placed — NOT iNat GPS.
- **Future per-instance ↔ observation linkage:** do it via an iNaturalist **Observation Field "PSBP Placement"**
  filled at capture time (human-asserted, GPS-independent) — NOT by GPS coordinate matching (a dead end by
  design). This also enables future per-instance phenology.
